# Facebook Login : diagnostic, déploiement et permissions

## Diagnostic

Le journal local du 1er octobre 2026 contient une `InvalidStateException` Socialite lors du callback. Cela signifie que le `state` renvoyé par Facebook ne correspondait pas à celui conservé dans la session Laravel. La cause précise sur Hostinger doit être vérifiée avec **ses propres logs** : le journal local ne prouve pas à lui seul ce qui s'y produit.

Un défaut de configuration local était certain : `APP_URL` se terminait par `/` et `FACEBOOK_REDIRECT_URI="${APP_URL}/auth/facebook/callback"` produisait `//auth/facebook/callback`. Le callback est désormais construit depuis `APP_URL` canonique, sans utiliser `FACEBOOK_REDIRECT_URI`. La connexion démarre sur le même domaine que ce callback. `state` reste obligatoire.

L'ancien contrôleur rejetait également toute identité Facebook sans e-mail, et liait automatiquement un compte Spotlight de même adresse. Le nouveau parcours demande l'e-mail manquant après connexion et n'associe jamais des comptes sur la seule concordance de l'adresse. Un citoyen déjà inscrit par mot de passe peut lier volontairement Facebook depuis **Profil**, après confirmation de son mot de passe. La colonne d'avatar a aussi été élargie pour accepter les longues URL Facebook. Le provider Socialite demandait par défaut `gender`, `verified` et `link` à Graph : Spotlight limite désormais les champs lus à `id`, `name`, `email` et `picture`, ce qui supprime des demandes inutiles pour les utilisateurs ordinaires. Sa version Graph utilise maintenant `META_GRAPH_VERSION`, comme le module de publication.

## Complétion du profil

Si Facebook fournit une adresse valide, elle est enregistrée et marquée vérifiée sans courriel Spotlight. La page de complétion n'affiche alors **aucun champ e-mail** et ne demande que le téléphone s'il manque. Si Facebook ne fournit pas d'adresse, l'utilisateur en saisit une dans Spotlight ; cette adresse reste non vérifiée jusqu'au clic sur le lien reçu par e-mail. Un téléphone déjà enregistré n'est ni redemandé ni écrasé.

`users.email_source` distingue `facebook` de `manual`. Une adresse saisie ou modifiée dans Spotlight ne devient pas vérifiée lors d'une connexion Facebook ultérieure par simple liaison du compte. Pour les comptes antérieurs à cette colonne, la provenance est inconnue : une adresse non vérifiée n'est reconnue comme fournie par Facebook que si le callback retourne **exactement cette adresse**. Une adresse différente n'est jamais remplacée automatiquement. La vérification classique conserve son parcours.

Avant la correction, le formulaire rendait un champ e-mail désactivé même quand l'adresse était déjà présente ; sa présence à l'écran ne prouvait donc pas une absence de réponse Facebook. Après déploiement, la ligne `Connexion Facebook reussie Spotlight` indique seulement `facebook_email_received`, `facebook_email_usable` et `email_stored` (booléens). Elle ne contient ni adresse ni jeton. Ces valeurs permettent de distinguer un e-mail absent/refusé par Meta d'un éventuel défaut de traitement local.

## Déploiement Hostinger

1. Sauvegarder la base et le fichier `.env`, puis déployer le code. Ne jamais mettre `.env` dans Git.
2. Dans l'environnement de production, définir `APP_URL=https://spotlight.kirovadigital.com` (sans slash final), `APP_ENV=production`, `APP_DEBUG=false`, `SESSION_DRIVER=database`, `SESSION_DOMAIN=null`, `SESSION_SECURE_COOKIE=true` et `SESSION_SAME_SITE=lax`. Conserver le même `APP_KEY` sur tous les processus. Ne pas utiliser `FACEBOOK_REDIRECT_URI` : il est ignoré pour éviter un domaine ou un chemin de callback divergent. Forcer HTTPS au niveau du site.
3. Dans Facebook Login, enregistrer exactement `https://spotlight.kirovadigital.com/auth/facebook/callback` comme **URI de redirection OAuth valide**. Le domaine utilisé pour ouvrir Spotlight doit être le même, sans variante `www` ou ancien tunnel. Vérifier que l'application est Live et que `public_profile` et `email` sont disponibles pour les utilisateurs ordinaires. Aucun SDK JavaScript Facebook n'est nécessaire ici : Socialite réalise le flux serveur.
4. Sur Hostinger, déployer aussi les assets Vite construits (`npm ci && npm run build` en environnement de build), puis exécuter `composer install --no-dev --optimize-autoloader`, `php artisan migrate --force`, `php artisan config:clear`, `php artisan config:cache`, `php artisan route:cache` et `php artisan view:cache`. La nouvelle migration ajoute `users.email_source` sans supprimer ni modifier les adresses existantes. La migration précédente rendait déjà `users.email` nullable pour les nouveaux inscrits Facebook sans e-mail ; l'inscription classique garde sa validation obligatoire. La table `sessions` doit exister si `SESSION_DRIVER=database`. Un worker de queue supervisé reste nécessaire pour les publications et notifications asynchrones du projet, mais pas pour le callback Facebook lui-même.
5. Faire un essai en navigation privée avec un compte Facebook **sans rôle dans l'application Meta**, d'abord sur l'adresse canonique. Vérifier le retour vers la page de complétion, le téléphone, puis l'e-mail et son lien de vérification lorsque Facebook ne fournit pas d'adresse. Ne pas publier de déclaration réelle pour ce test.

Si le callback échoue, consulter les nouveaux événements `Etat OAuth Facebook invalide Spotlight` ou `Connexion Facebook echouee Spotlight` dans `storage/logs/laravel.log`. `has_session_cookie=false` suggère un souci de cookie/domaine/HTTPS ; `has_session_state=false` malgré un cookie suggère une session Laravel non conservée (base, configuration, `APP_KEY`, déploiement sur plusieurs instances ou navigation entre domaines). Si les deux sont vrais, vérifier aussi les onglets multiples et l'expiration du flux. Un échec HTTP Meta est consigné uniquement par statut et codes d'erreur, jamais par token ou réponse complète.

## Permissions Meta

La connexion **citoyenne** demande uniquement `public_profile` et `email` dans `FacebookAuthController`. Elle n'utilise ni le jeton de Page, ni les permissions de publication. `MetaPublishingService` utilise séparément un `META_PAGE_ACCESS_TOKEN` configuré côté serveur. Les scopes ne sont pas écrits dans ses appels Graph : la nécessité ci-dessous est déduite des endpoints utilisés et doit être confirmée selon le type de jeton Meta et les règles d'App Review en vigueur.

| Permission | Usage réel dans Spotlight | Nécessaire actuellement ? | Démonstration honnête pour Meta |
| --- | --- | --- | --- |
| `pages_read_user_content` | Aucun appel de lecture des publications ou commentaires créés par des tiers sur la Page. | Non. | Aucune vidéo justificative possible ; ne pas demander. |
| `pages_manage_posts` | `MetaPublishingService::publishToFacebook()` écrit sur `/{page_id}/photos` ou `/{page_id}/feed`, y compris les rappels. | Oui pour la publication Facebook avec le jeton de Page approprié. | Depuis la modération, montrer une publication sur une Page de test contrôlée puis la publication visible sur cette Page. |
| `instagram_content_publish` | `publishToInstagram()` crée un conteneur `/{ig_id}/media`, attend son état puis appelle `/{ig_id}/media_publish`. | Oui pour publier sur Instagram professionnel. | Montrer la validation, la création de l'avis Instagram sur un compte professionnel de test, puis son lien dans Spotlight. |
| `instagram_basic` | Le code utilise un ID Instagram configuré et les endpoints Instagram Graph ; il ne lit pas de profil citoyen. | Oui dans le modèle Instagram API avec Facebook Login associé à une Page. | Montrer le compte professionnel relié à la Page et le résultat de la publication, sans prétendre lire les profils des citoyens. |
| `business_management` | Aucun appel Business Manager/Business Assets dans le code. | Non pour le parcours actuel. | Aucune vidéo justificative possible ; ne pas demander. |
| `pages_show_list` | Aucun appel `GET /me/accounts` dans l'application ; ID de Page et jeton fournis par configuration. | Pas utilisé dans l'application actuelle. Peut être nécessaire lors d'un futur flux de sélection/autorisation de Pages, pas pour le login citoyen. | Aucune sélection de Page dans Spotlight à montrer aujourd'hui ; ne pas inventer cette fonction. |
| `pages_read_engagement` | `facebookPhotoUrl()` lit `images` sur la photo publiée ; `publicPostUrl()` lit `link`/`permalink`. `meta:status` lit aussi l'ID de Page. | Potentiellement nécessaire à ces lectures et au flux Instagram avec Facebook Login ; confirmer avec le jeton de Page utilisé. | Montrer, sur Page de test, la photo et les liens Facebook/Instagram récupérés après publication. |
